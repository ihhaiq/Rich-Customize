# تصدير HTML

زر `📋 نسخ HTML` بجانب المعاينة يستدعي `r:exporthtml`. يقرأ نسخة من بيانات
FSM بدون تحميل المسودة الذي يحدّث موضع التمرير، وبدون حفظ أو تعديل history.

`build_input_rich_message_html()` يستدعي `build_input_rich_message()`، نفس بناء
النشر والمعاينة، ثم يحوّل الناتج بواسطة `rich_html.py`. هذا الملف يجمع دوال
التحويل التي كانت داخل parser، ويستخدمه الاستيراد والتصدير معًا. لذلك لا نعتمد
على حقول HTML المخزونة التي قد تختلف عن native_data أو rich_text الفعلي.

- الحد `len(code) <= 25_000` يُحسب على HTML الخام قبل escaping: نقاط Unicode،
  وليس بايتات UTF-8 أو وحدات UTF-16. الإيموجي المركّب قد يحتوي عدة نقاط Unicode.
- الكود القصير يظهر كنص حرفي في فقرة داخل رسالة Rich منفصلة، بين عنوان وفاصلين
  وتذييل. لا نستخدم preformatted أو CopyTextButton، ونعطّل اكتشاف الروابط وحماية
  المحتوى في رسالة التصدير حتى يبقى النص قابلًا للتحديد والنسخ.
- الكود الأطول يُرسل كاملًا في ملف UTF-8 واحد، دون BOM أو سطر إضافي أو تقسيم.
- أسماء الصفحات تُحفظ بالعربية، مع تنظيف محارف المسارات في اسم الملف فقط.
- أخطاء التوليد والإرسال تُسجّل، ويصل للمستخدم تنبيه مختصر بدون تفاصيل الاستثناء.

التصدير هو HTML لمحتوى Rich، بما فيه أزرار Rich والـcredit الذي يمثل الكاتب.
لوحة Inline الخارجية تبقى `reply_markup` منفصلة كما في النشر، ولا تتحول إلى
أزرار داخل المحتوى. كذلك HTML لا يضمّن ملفات الوسائط: يحتفظ بمراجع
`tg://photo?id=m_0` وما شابهها. دالة البناء تعيد معها `media` عند الاستخدام
البرمجي؛ إعادة إرسال HTML يحتوي هذه المراجع تتطلب تمرير قائمة الوسائط أيضًا.
ملف النص المطلوب يحتوي HTML فقط.

مرجع صيغة الوسوم: [Telegram Rich HTML](https://core.telegram.org/bots/api#rich-html-style).
اختبارات الميزة في `tests/test_html_export.py` تستخدم إرسالًا وهميًا؛ تجربة تحديد
النص ونسخه فعليًا تحتاج عميل Telegram يدعم Rich Messages.
