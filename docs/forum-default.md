# موضوع النشر الافتراضي — `/default`

## السلوك

- يستطيع مالك المجموعة أو أي مسؤول إرسال `/default` **داخل الموضوع المقصود**. الإعداد محفوظ لكل مجموعة، وليس لكل حساب.
- آخر تعيين معتمد يحل محل السابق. في المجموعات ذات المواضيع، **لا ينشر البوت في «العام» تلقائياً** إذا لم يتم اختيار موضوع.
- إرسال `/default` صراحةً في «العام» يضبط العام كوجهة، إذا لم يرفق تليكرام `message_thread_id` (يُحفظ داخلياً بالرقم 0). هذا ليس مسار احتياطي صامت.
- `/default status`: عرض الموضوع الحالي، أو توضيح أن النشر متوقف.
- `/default clear`: حذف التعيين وإيقاف نشر هذه المجموعة إلى أن يحدد مسؤول موضوعاً جديداً.
- المسؤولون المخفيون (Anonymous Admin) مدعومون فقط عندما يثبت `sender_chat.id` أنه نفس معرّف المجموعة. `/default@OtherBot` لا يعالَج.
- في القنوات والمجموعات التي **لا** تستخدم المواضيع تبقى طريقة النشر السابقة كما هي، بشرط ألا يكون لديها تعيين قديم لموضوع لم يعد مدعوماً.

## النشر إلى عدة مجموعات

- كل وجهة تُنفَّذ مستقلة، دون تسريب المنشور إلى «العام» أو تحويله تلقائياً إلى موضوع آخر.
- عند غلق الموضوع: خطأ `PUBLISH_TOPIC_CLOSED`. عند حذفه: `PUBLISH_TOPIC_DELETED`. عند غياب الإعداد: `PUBLISH_TOPIC_NOT_SET`. عند عدم صلاحية المعرف: `PUBLISH_THREAD_INVALID`.
- فشل مجموعة واحدة لا يوقف النشر إلى المجموعات الأخرى. تقرير النشر اليدوي يذكر العدد والوجهات الفاشلة وأسبابها.
- `RCB1` الخاص بالتطبيق المصغر يعرض سبب الفشل للوجهة المختارة. **الجدولة** تفحص التعيين عند التنفيذ وتخزن رمز فشل كل وجهة، ثم ترسل ملخصاً لصاحب الجدولة بالمجموعات التي نجحت وفشلت. قد يتغير الموضوع الافتراضي بين إنشاء الجدولة وموعد التنفيذ؛ يعتمد النظام التعيين الساري وقت التنفيذ.

## الحدود

- Bot API لا يتيح جلب كل المواضيع القائمة عبر قائمة استعلام مباشرة؛ لهذا السبب تتم التهيئة من داخل الموضوع.
- لا يمكن ضمان اكتشاف موضوع مغلق قبل طلب الإرسال إذا تغيّر وضعه دون تحديث مرئي؛ نتيجة Telegram النهائية تحدد نجاح الإرسال أو سبب رفضه.
- النشر إلى الموضوع العام يحدث فقط إذا اختاره مسؤول صراحةً، أو في مجموعة لا تدعم المواضيع.

## الترحيل والنشر

1. نفذ الاختبارات على نسخة من قاعدة البيانات قبل الإنتاج.
2. يحتوي `tgcloud/schema.js` جدولاً جديداً `forum_topic_defaults`، وعمود `failure_code` في `scheduled_post_destinations`. يجب تنفيذ `tgcloud migrate` أولاً **بعد مراجعة الفروقات والنسخ الاحتياطية**.
3. بعد نجاح الترحيل والاختبارات، نفذ `tgcloud push` ثم `tgcloud webhook sync`، وتحقق من استقبال أمر `/default` في المجموعة.
4. تحديث التطبيق المصغر `app/miniapp_static/app.js` يحتاج نشر Cloudflare Pages من نفس الفرع.
5. **لا تنشر كود Serverless قبل تعديل مخطط قاعدة البيانات**. لا تنفذ الترحيل أو النشر للإنتاج آلياً دون موافقة صريحة.

## حالات اختبار

- مسؤول / غير مسؤول / مسؤول مخفي / أمر موجّه لبوت آخر.
- أمر داخل موضوع برقم صالح؛ أمر في «العام»؛ `status` و`clear`.
- مجموعتان صالحتان ومجموعة موضوعها مغلق: ينجح إرسال مجموعتين، وتظهر الثالثة بخطأ واضح.
- نشر مباشر، وRCB1، وجدولة بنتيجة `partially_sent` عند وجود فشل مؤكد.
